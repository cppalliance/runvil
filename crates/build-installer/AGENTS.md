# build-installer

- Nothing here builds Workshop or the Gateway. Both come from the Workshop checkout `RUNVIL_WORKSHOP` names. `cargo workshop bundle`, run there, builds Workshop's Tauri bundle (`bundle_command` in `src/main/workshop.rs`). The Gateway is the release that checkout's `gateway-pin/pin.json` names, from `--gateway-binary`, `RUNVIL_GATEWAY_SIDECAR`, or the file the checkout's `tools/fetch-gateway-sidecar.mjs` stages (`src/main/gateway.rs`). A Windows installer is the NSIS setup from that bundle, which already holds the Gateway, so only a macOS or Linux build reads the Gateway and the pin. The build leaves both checkouts clean: it writes only to Cargo's target directories.
- The installer mode checks the Workshop checkout before any command runs (`check` in `src/main/workshop.rs`). The `[workspace.package]` version in its `Cargo.toml` must equal this workspace's, because the release file names and the release tag check in `.github/workflows/installers.yml` use this workspace's version while Tauri names its files with Workshop's. The `[toolchain]` channel in its `rust-toolchain.toml` must equal this repository's, because the Cargo that runs the installer builds Workshop. A change of `rev` in the root `Cargo.toml`'s `[workspace.metadata.workshop]` to a Workshop commit that changed either value changes the workspace version or `rust-toolchain.toml` with it.
- Each release file name has one definition: `installer_name` and `workshop_updater_name` in `src/main/installer/collect.rs`. The installer build, the IFW stage, and the `manifest` mode call them; never spell a release name inline. The payload's bundle and AppImage names are the constants beside them, which must equal those `crates/workshop/gateway-discovery/src/peer.rs` in the Workshop checkout searches; a test in `src/main/tests/collect.rs` compares the two. It is the one test that reads the real checkout, the one `RUNVIL_WORKSHOP` names when the test runs; every other test builds its own Workshop tree in a temporary directory. The bare Gateway executable's name is `GATEWAY` in `collect.rs`.
- The Qt IFW pin is enforced in two places that change together: `IFW_VERSION` in `src/main/installer/ifw.rs`, and each `ifw-archive` with its `ifw-sha256` in `.github/workflows/installers.yml`'s build matrix. `USAGE` in `src/main/args.rs`, the workflow step's name, and this crate's README name the version or the archive paths too; update them in the same change.
- Files under `ifw/` are templates. The build fills `{{NAME}}` placeholders and fails on any left over; IFW's own `@Variable@` placeholders are left for IFW to expand at install time.
- `installscript.qs` runs only inside IFW and has no test support. A change to either script, or to what an install puts where, updates the install cells in `.github/installers/cell.sh` and `cell.ps1`, which are its tests.
